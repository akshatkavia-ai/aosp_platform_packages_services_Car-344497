# Android Automotive Car Services Repository Overview

## Overview

This document summarizes the current structure of the Android Automotive car services repository under `packages/services/Car`. The overview is based on the repository's build files, service manifests, core service implementations, client API entry points, product packaging definitions, and representative auxiliary modules. The repository is a platform-style Android Open Source Project monorepo that combines framework APIs, system services, hardware abstraction integrations, native utilities, support libraries, sample applications, and test assets for in-vehicle Android systems.

The repository also includes C and C++ native components, such as `procfs-inspector/server/Android.mk` and `evs/app/Android.mk`, plus AIDL interfaces in modules like `car-lib/Android.bp`. The manifest at `service/AndroidManifest.xml` declares the `.CarService` service with an intent filter for `android.car.ICar`. In `onCreate()`, the service connects to the vehicle HAL, constructs `ICarImpl`, initializes it, and registers the binder service with `ServiceManager.addService("car_service", mICarImpl)`. |
| Client API entry point | The main client entry point is `android.car.Car` in `car-lib/src/android/car/Car.java`. Applications and platform components call `Car.createCar(...)`, which verifies the automotive feature, and then `connect()`, which binds to package `com.android.car` using the action `android.car.ICar`. Clients then call `getCarManager(String)` to retrieve binder-backed service managers such as audio, power, property, package, projection, cluster, VMS, and driving state managers. |
| Service implementation hub | The binder-facing implementation hub is `service/src/com/android/car/ICarImpl.java`, which extends `ICar.Stub`. This class owns the `VehicleHal` instance and wires together many platform services, including power, property, input, projection, audio, driving state, UX restrictions, package policy, instrument cluster, Bluetooth, diagnostics, storage monitoring, configuration, VMS, and user services. Its `getCarService(String)` method exposes these managers over binder based on the requested `Car` service name. |
| Hardware integration layer | The repository has a dedicated hardware integration layer centered on `service/src/com/android/car/hal/VehicleHal.java`. This class wraps the HIDL `android.hardware.automotive.vehicle.V2_0.IVehicle` interface, initializes HAL services, manages property subscriptions, fetches and sets vehicle properties, dispatches property events to specific HAL service handlers, and reconnects after HAL restarts. `CarService` obtains `IVehicle` through `IVehicle.getService()`, showing that the platform service depends on the Android Automotive vehicle HAL rather than generic network transport. |
| Network layers | There is no conventional HTTP or RPC network layer at the center of this repository. The dominant communication mechanisms are Android Binder IPC between clients and `CarService`, Android system service registration through `ServiceManager`, and hardware-facing HIDL communication to the vehicle HAL through `IVehicle`. The product definition in `car_product/build/car.mk` does mention a location overlay for Google network and fused location providers, but that is product configuration rather than a repository-wide application network stack. |
| IPC and integration model | The integration model is primarily in-process platform code plus binder and HAL boundaries. `CarService` publishes `car_service` through the Android service manager, `android.car.Car` binds using the `android.car.ICar` interface, and `ICarImpl` returns service-specific binders to callers. At the hardware boundary, `VehicleHal` communicates with the vehicle HAL service, while some auxiliary native modules, such as `procfs-inspector`, also depend on binder libraries. |
| Platform packaging entry points | Product assembly is driven in part by `car_product/build/car.mk`, which adds packages such as `CarService`, `android.car`, `car-frameworks-service`, `com.android.car.procfsinspector`, `CarUsbHandler`, `CarMapsPlaceholder`, and several car applications to the system image. | Core API modules | `car-lib` is the main Android car API library and contains the public and system automotive client APIs under `android.car`. It includes binder-facing access through `Car.java` and native integration pieces such as `libcarpowermanager` defined in `car-lib/Android.bp`. `car-support-lib` provides a support-layer wrapper, and `car-support-lib/src/android/support/car/CarServiceLoaderEmbedded.java` shows that it delegates to the embedded `android.car.Car` runtime and wraps selected managers for support-library consumers. |
| Core system-service modules | The `service` module is the central automotive service package. `CarService.java` is the Android service entry point, `ICarImpl.java` is the binder implementation hub, and the module build file `service/Android.mk` packages the app as `CarService` and links against `android.car`, HIDL automotive Java libraries, `vehicle-hal-support-lib`, `car-frameworks-service`, `car-systemtest`, and the procfs inspector client library. |
| HAL support and testing modules | `vehicle-hal-support-lib` is a static Java library built from its `src` tree and linked against automotive HIDL vehicle Java libraries and JUnit according to `vehicle-hal-support-lib/Android.mk`. It supports HAL-oriented testing and helper functionality used by other modules such as the main car service test configurations. |
| Auxiliary service modules | The repository includes auxiliary modules such as `car-default-input-service`, which exposes `android.car.input.service.DefaultInputService` as a service protected by `android.car.permission.BIND_CAR_INPUT_SERVICE`. The implementation in `DefaultInputService.java` extends `CarInputHandlingService` and acts as a sample or default key-event handler. The repo also includes `car-usb-handler`, `car-maps-placeholder`, and `TrustAgent`, each representing focused automotive support components. |
| Native tooling and diagnostics modules | The repository contains native utilities and diagnostics-oriented modules. `procfs-inspector/server/Android.mk` builds the native executable `com.android.car.procfsinspector` from C++ sources such as `main.cpp`, `server.cpp`, and `process.cpp`, and links against binder, log, and utils libraries. This indicates native process-inspection support rather than a web-facing service layer. |
| EVS and graphics modules | The `evs` subtree contains Extended View System related components. ## Notable Verified Entry and Integration Paths

The service startup path is directly visible in the code. The manifest declares `.CarService`, and `CarService.onCreate()` acquires the vehicle HAL with `IVehicle.getService()`, constructs `ICarImpl`, initializes it, links a death recipient to the HAL, and registers `car_service` with the Android service manager. This confirms that the repository's most important runtime entry point is a persistent Android system service rather than a standalone executable or network server.

The client connection path is equally explicit in `android.car.Car`. The `startCarService()` method binds to the package `com.android.car` with the action `android.car.ICar`, the service connection wraps the remote binder as `ICar`, and `getCarManager(String)` asks `ICarImpl` for a service-specific binder. This establishes Binder IPC as the main application-facing integration boundary.

The hardware-facing path is implemented by `VehicleHal`. That class wraps the `IVehicle` HIDL service, loads property configurations, assigns properties to specialized HAL handlers, supports property subscription and event dispatch, and reconnects after HAL death. This confirms that the repository's lower integration layer is the Android Automotive vehicle HAL, not a TCP, REST, or message-broker network stack.
